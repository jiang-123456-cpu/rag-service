# 企业级 RAG 知识库智能问答系统 — 项目亮点与面试指南

## 一、项目概述

基于 FastAPI 构建的企业级 RAG（检索增强生成）知识库问答系统，支持多知识库管理、多格式文档上传解析、混合检索 + 重排序、LangGraph Agent 流式问答、JWT 鉴权与角色权限控制。

**技术栈**：FastAPI + LangChain + LangGraph + ChromaDB + MySQL(async) + 阿里云通义千问 + dashscope

---

## 二、六大核心亮点

### 亮点 1：混合检索 + Rerank 二次排序（检索精度）

**是什么**：不依赖单一检索方式，而是同时使用向量语义检索（Chroma）和关键词精确检索（BM25），再通过 EnsembleRetriever 加权融合，最后用专门的 Rerank 模型二次精排。

**怎么实现的**：

```
用户 Query
  ├─→ Chroma 向量检索 (k=2, 语义相似度)
  ├─→ BM25 关键词检索 (TF-IDF 统计匹配)
  ↓
EnsembleRetriever (权重 0.5 / 0.5 融合)
  ↓
dashscope TextReRank (qwen3-rerank 模型精排)
  ↓
Top-K 文档 → 注入 Prompt → LLM 生成回答
```

**关键代码路径**：`services/vector_service.py` → `get_retriever()` 方法
- 每个知识库用独立的 Chroma collection（`kb_{kb_id}`）隔离
- `EnsembleRetriever(retrievers=[vector_retriever, bm25_retriever], weights=[0.5, 0.5])`
- 重排序在 `services/rag_service.py` → `ask()` 方法中调用 `recorder_service.reorder_documents()`

**为什么这样做**：
- 向量检索擅长理解语义（"怎么部署" 能匹配到 "如何上线"），但会漏掉精确关键词匹配
- BM25 擅长关键词精确匹配（专有名词、代码片段），但缺乏语义理解
- 两者互补 + Rerank 精排 = 兼顾召回率和精确率

---

### 亮点 2：LangGraph Agent + 流式 SSE 响应（用户体验）

**是什么**：用 LangGraph 的 `create_agent` 构建智能体，通过 MemorySaver 实现多轮对话记忆，配合 FastAPI 的 StreamingResponse 实现逐字流式输出（SSE），用户无需等待完整回答生成。

**怎么实现的**：

`agent/agent.py` → `AgentFactory` 类（单例模式）：
- `create_agent()`：每次调用动态创建 Agent，注入 tools、system_prompt、model_config
- `MemorySaver` 作为 checkpointer，通过 `thread_id` 隔离不同会话的记忆
- `astream_content()`：异步生成器，`stream_mode="messages"` 逐 token 产出

`routers/chat.py` → `/api/chat/ask`：
- 用 `StreamingResponse` + `text/event-stream` 返回 SSE 流
- 事件类型分三种：`sources`（参考来源）→ `content`（流式回答）→ `done`（结束）
- 回答完成后异步写入 `ConversationHistory` 表持久化对话记录

**踩过的坑（也是面试加分项）**：
1. **config 参数传递**：langgraph 的 `astream/ainvoke` 第二个参数是 `config: RunnableConfig`，`configurable` 必须嵌套在 config 字典里，不能作为顶层 kwarg 展开
2. **stream tuple 索引**：`stream_mode="messages"` 产出的是 `(message_chunk, metadata)` 二元组，`event[0]` 是消息内容，`event[1]` 是元数据

---

### 亮点 3：多知识库隔离 + 多格式文档解析（工程能力）

**是什么**：支持创建多个独立知识库，每个知识库在向量库中用独立 collection 隔离；支持 txt/pdf/md/docx 四种格式，docx 还深度解析表格、页眉页脚、文本框。

**怎么实现的**：

**多知识库隔离**（`vector_service.py`）：
- `_get_collection_name(kb_id)` → `f"kb_{kb_id}"`
- 上传文档时按 kb_id 创建/写入对应 collection
- 检索时也按 kb_id 从对应 collection 检索

**文档解析**（`utils/file_handler.py` → `get_file_documents()`）：
- txt → `TextLoader`
- pdf → `PyPDFLoader`
- md → 直接读取 UTF-8 文本
- docx → python-docx 深度解析：
  1. 正文段落
  2. 表格内容（高频遗漏点）
  3. 页眉页脚
  4. 文本框（通过底层 XML `//w:txbxContent` 提取）

**文档分块**（`vector_service.py`）：
- `RecursiveCharacterTextSplitter`：chunk_size=200, chunk_overlap=20
- 分隔符优先级：`\n\n` → `\n` → `.` → `!` → `?` → `。` → `！` → `？` → 空格

**MD5 去重**（`utils/file_handler.py`）：
- 上传前计算文件 MD5，与 `md5.txt` 中已存指纹比对
- 重复文件直接拒绝上传，避免重复入库

---

### 亮点 4：Agent 工具系统 + 中间件 Hook（扩展性）

**是什么**：为 Agent 配备了可插拔的工具集（RAG 检索、重排序、时间查询、用户信息解析、天气查询），并通过中间件在 Agent/Model/Tool 执行前后插入 Hook 做日志和监控。

**怎么实现的**：

**工具系统**（`agent/agent_tools.py`）：
- `@tool` 装饰器定义工具，LangChain 自动提取函数签名和 docstring 作为工具描述
- `rag_summary_tools`：封装 RAG 检索 + 摘要生成
- `reorder_documents_tools`：封装重排序服务
- `what_time_is_now` / `get_user_info_tools` / `get_weather_tools`：辅助工具
- 工具通过 `AgentFactory.create_agent(tools=[...])` 动态注入

**中间件**（`agent/agent_middleware.py`）：
- `@before_agent` / `@after_agent`：Agent 执行前后
- `@before_model` / `@after_model`：模型调用前后
- `@wrap_model_call` / `@wrap_tool_call`：包装模型/工具调用
- `get_middleware()` 返回所有 hook 列表，可按需装配

---

### 亮点 5：全链路异步架构（性能）

**是什么**：从数据库到 LLM 调用全链路异步，阻塞操作用 `asyncio.to_thread` 包装，避免 FastAPI 事件循环被阻塞。

**怎么实现的**：

- **数据库层**：SQLAlchemy 2.0 async session（`AsyncSessionLocal`），所有查询用 `await db.execute()`
- **检索层**：`retriever.invoke()` 是同步阻塞的，用 `await asyncio.to_thread(retriever.invoke, query)` 包装
- **RAG 链**：`rag_chain.invoke()` 同步阻塞，同样用 `asyncio.to_thread` 包装
- **JWT 解码**：`jwt.decode()` 用 `await asyncio.to_thread(jwt.decode, ...)` 包装
- **密码哈希**：`bcrypt.hashpw()` 在 lifespan 中用 `asyncio.to_thread` 包装
- **LLM 调用**：`agent.astream()` 原生异步

---

### 亮点 6：分层 Prompt 工程 + 对话历史持久化（业务深度）

**是什么**：三层提示词体系（系统提示词 → RAG 摘要提示词 → 报告生成提示词），从 YAML 配置加载；对话历史持久化到 MySQL，支持分页查询。

**怎么实现的**：

**Prompt 层**（`config/prompts.yml` + `prompts/*.txt` + `utils/prompt_loader.py`）：
- `main_prompt.txt`：系统角色定义（企业级 RAG 助手，要求引用来源、不编造）
- `rag_summarize.txt`：信息压缩与融合专家（去重、合并、按逻辑重组织、300字以内）
- `report_prompt.txt`：报告生成（标题/概述/发现/分析/建议/参考资料的 Markdown 结构）
- `prompt_loader.py`：从 YAML 读取路径，加载为字符串，运行时注入

**对话历史**（`routers/chat.py` → `/api/chat/list`）：
- 每次问答完成后，将 question + answer + kb_name + questioner 写入 `ConversationHistory` 表
- 支持按 kb_id 过滤、分页查询（page + page_size）
- 按创建时间倒序排列

## 三、面试官可能的问题与参考回答

### Q1: 你这个项目的整体架构是怎样的？数据流是什么？

**回答**：

> 整体是四层架构：API 层、Agent 层、检索层、存储层。
>
> 数据流是：用户发起问答请求 → FastAPI 路由先做 JWT 认证和参数校验 → RagService 从 Chroma 向量库做混合检索（向量 + BM25）→ 检索结果交给 Rerank 模型精排 → 排好序的文档拼入 System Prompt → AgentFactory 创建 LangGraph Agent 调用大模型流式生成 → 通过 SSE 逐字返回给前端 → 最后异步把对话记录写进 MySQL。
>
> 文档上传是另一条线：用户上传文件 → MD5 去重校验 → 根据文件类型用对应 Loader 解析（docx 会深度提取表格/页眉页脚/文本框）→ RecursiveCharacterTextSplitter 分块 → 写入对应知识库的 Chroma collection → 同时在 MySQL 记录文档元数据。

---

### Q2: 为什么用混合检索？单纯向量检索不行吗？

**回答**：

> 单纯向量检索有明显短板：它擅长语义理解，比如用户问"怎么部署"能匹配到"如何上线"，但对专有名词、代码片段、人名等精确关键词的匹配能力弱。比如用户搜"FastAPI"这个词，向量检索可能返回语义相近但不含这个词的文档。
>
> BM25 是基于 TF-IDF 的统计方法，恰好相反——对精确关键词匹配很强，但缺乏语义理解，"怎么部署"匹配不到写"如何上线"的文档。
>
> 所以我用 EnsembleRetriever 以 0.5/0.5 的权重融合两者结果，兼顾召回率和精确率。但融合后的排序还是基于各自分数的简单加权，精度不够，所以又加了一层 Rerank——用专门的 qwen3-rerank 模型对候选文档做交叉注意力精排，把最相关的排到前面，只取 Top-K 注入 Prompt。
>
> 这是业界 RAG 系统的标准做法：Recall（多路召回）→ Rerank（精排）→ Top-K 注入。

---

### Q3: 你用 LangGraph 的 Agent 做了什么？为什么要用 Agent 而不是直接调 LLM？

**回答**：

> 直接调 LLM 就是"无状态的一问一答"，有两个问题：一是没有工具调用能力，LLM 只能靠自己的参数知识回答，无法检索私有知识库；二是没有多轮记忆，用户每次提问都要把完整上下文重传一遍。
>
> 我用 LangGraph 的 create_agent 做了几件事：
> 1. **工具注入**：Agent 可以自主决定是否调用 RAG 检索工具、重排序工具、时间查询工具等，而不是把所有逻辑硬编码在链里
> 2. **多轮对话记忆**：MemorySaver 作为 checkpointer，用 thread_id 隔离不同用户的会话，Agent 能记住上下文
> 3. **流式输出**：通过 stream_mode="messages" 逐 token 产出，配合 SSE 实现打字机效果
>
> AgentFactory 用了单例模式，全局只创建一次，避免每次请求都初始化 MemorySaver。但每次调用 create_agent 时会动态创建新的 Agent 实例，注入当前请求的 tools 和 system_prompt，保证请求间隔离。

---

### Q4: 你的流式输出是怎么实现的？踩过什么坑？

**回答**：

> 前后端都用 SSE（Server-Sent Events）。后端用 FastAPI 的 StreamingResponse，media_type 设为 text/event-stream，关键 header 是 `X-Accel-Buffering: no`（防止 Nginx 缓冲）。生成器函数里按 `sources → content → done` 的顺序 yield JSON 行。
>
> 踩过两个很隐蔽的坑：
>
> **坑一：configurable 参数传递**。langgraph 的 astream/ainvoke 第二个参数是 config: RunnableConfig，configurable 必须嵌套在 config 字典里。我一开始用 `**config_kwargs` 把 configurable 展开成顶层 kwarg，导致 checkpointer 永远找不到 thread_id，抛出 "Checkpointer requires configurable keys" 错误。修复方式是改成 `config={"configurable": {"thread_id": "..."}}`。
>
> **坑二：stream tuple 索引**。stream_mode="messages" 产出的是 (message_chunk, metadata) 二元组。我一开始用 event[1] 取消息，但 event[1] 永远是 metadata dict，isinstance(AIMessageChunk) 判断永远 False，所以生成器一个 chunk 都不 yield，前端就显示"暂无回答"。改成 event[0] 后才正常。
>
> 这两个 bug 叠在一起，表现就是"无论问什么都返回暂无回答"，因为第一个 bug 导致异常被 catch，第二个 bug 导致即使不报错也不产出内容。

---

### Q5: 你的文档解析做了哪些处理？docx 为什么要那么复杂？

**回答**：

> 支持 txt、pdf、md、docx 四种格式。txt 用 LangChain 的 TextLoader，pdf 用 PyPDFLoader，md 直接读 UTF-8。docx 是重点，用 python-docx 做了四层深度提取：
>
> 1. 正文段落（最基本的）
> 2. 表格内容（这是高频遗漏点，很多 RAG 系统只提取正文，表格里的数据全丢了）
> 3. 页眉页脚（企业文档的版本号、密级等信息常在页眉页脚）
> 4. 文本框（通过底层 XML `//w:txbxContent` 路径提取，python-docx 的 API 不直接暴露文本框）
>
> 为什么这么复杂？因为企业知识库的文档结构很乱——有些文档的关键信息在表格里，有些在文本框里。如果只提取正文段落，检索结果就会缺失大量关键信息，RAG 回答质量直接下降。
>
> 解析后用 RecursiveCharacterTextSplitter 分块，chunk_size=200, overlap=20。分块时给每个 chunk 打上 metadata（doc_id、file_path、chunk_index），方便后续溯源和删除。

---

### Q6: 你的多知识库是怎么隔离的？为什么要隔离？

**回答**：

> 用 ChromaDB 的 collection 机制隔离，每个知识库对应一个独立的 collection，命名规则是 `kb_{kb_id}`。
>
> 上传文档时，VectorStore 根据 kb_id 创建或获取对应 collection 写入。检索时也是按 kb_id 从对应 collection 检索，不会跨知识库搜索。
>
> 为什么要隔离？因为不同知识库的内容可能完全不同——比如一个存技术文档，一个存 HR 制度。如果混在一起检索，用户问技术问题时会返回 HR 文档，既浪费 Token 又影响回答质量。隔离后每个知识库就是一个独立的语义空间，检索精度更高。
>
> 同时 MySQL 里用 `knowledge_base` 和 `knowledge_document` 两张表做关系型管理，支持知识库的 CRUD、文档的增删、软删除（is_deleted 字段）、分页查询。

---

### Q7: 你提到全链路异步，具体哪些地方做了异步处理？

**回答**：

> FastAPI 本身是异步框架，但异步的关键不在于框架，而在于不能在 async 函数里调用同步阻塞操作——否则会阻塞整个事件循环，所有请求都卡住。
>
> 我做了这几层异步：
> 1. **数据库**：SQLAlchemy 2.0 async session，用 `AsyncSessionLocal` 创建会话，所有查询 `await db.execute()`
> 2. **向量检索**：`retriever.invoke()` 是 LangChain 的同步方法，用 `await asyncio.to_thread(retriever.invoke, query)` 包装，丢到线程池执行
> 3. **RAG 链**：`rag_chain.invoke()` 同样用 `asyncio.to_thread` 包装
> 4. **JWT 解码**：`jwt.decode()` 虽然快但也是同步的，用 `asyncio.to_thread` 包装
> 5. **密码哈希**：bcrypt 是 CPU 密集型操作，在 lifespan 里用 `asyncio.to_thread` 包装
> 6. **LLM 调用**：LangGraph 的 `agent.astream()` 原生支持异步
>
> 关键原则是：IO 密集型（数据库、网络）用 async 库；CPU 密集型或同步库用 `asyncio.to_thread` 包装。

---

### Q8: 你的 Agent 工具系统是怎么设计的？工具是怎么被调用的？

**回答**：

> 工具用 LangChain 的 `@tool` 装饰器定义，装饰器会自动提取函数签名作为参数 schema、docstring 作为工具描述。LLM 在推理时会根据用户问题自主决定是否调用工具、调用哪个工具、传什么参数。
>
> 我定义了五个工具：
> - `rag_summary_tools`：封装 RAG 检索 + 摘要生成，参数是 query 和 kb_id
> - `reorder_documents_tools`：封装重排序服务，参数是 query 和 documents 列表
> - `get_user_info_tools`：从 JWT token 解析用户 ID
> - `what_time_is_now`：获取当前时间
> - `get_weather_tools`：天气查询（演示用占位）
>
> 工具通过 `AgentFactory.create_agent(tools=[...])` 动态注入。不同场景可以注入不同的工具子集——比如普通用户不给 rerank 工具，管理员给全部工具。
>
> 另外还设计了中间件 Hook 系统：`@before_agent`、`@after_agent`、`@wrap_tool_call` 等，可以在工具调用前后插入日志、监控、参数校验等逻辑，不侵入业务代码。

---

### Q9: 你的 Rerank 用的什么模型？遇到什么问题？

**回答**：

> 用的是阿里云 dashscope 的 qwen3-rerank 模型，通过 `dashscope.TextReRank.call()` 调用。
>
> 遇到一个很隐蔽的 bug：dashscope 返回的结果结构里，相似度字段名是 `relevance_score` 而不是 `score`，文档内容是 `{"text": "..."}` 字典而不是纯字符串。但原代码取的是 `item.get("score", 0.0)` 和 `item.get("document", "")`——字段名错了导致相似度永远是 0，document 拿到的是字典导致后续匹配逻辑（`orig.page_content == text`）永远匹配不上，整个重排序静默失效。
>
> 修复方式是改成 `item.get("relevance_score", item.get("score", 0.0))` 兼容两种字段名，document 做类型判断：如果是 dict 就取 `doc.get("text", "")`。
>
> 这个 bug 之所以危险，是因为它不报错——重排序"成功"了，但结果和没排序一样，只是相似度全显示 0，很难发现。

---

### Q10: 如果让你优化这个项目，你会怎么做？

**回答**：

> 目前能想到几个方向：
>
> 1. **检索优化**：现在 BM25 的 weights 是固定 0.5/0.5，可以根据 query 类型动态调整——如果包含大量专有名词就提高 BM25 权重，如果是自然语言提问就提高向量权重
>
> 2. **分块策略**：现在用固定 chunk_size=200，对于长文档（如技术手册）会截断语义。可以改用语义分块（按段落/章节），或者用 LLM 做摘要式分块
>
> 3. **缓存层**：相同问题直接返回缓存结果，减少 LLM 调用成本。可以用 Redis 缓存 query → answer 的映射，设置 TTL
>
> 4. **并发控制**：目前每个请求都创建新的 Agent 实例，高并发下内存会涨。可以引入 Agent 池化或限流
>
> 5. **评估体系**：目前没有自动化的 RAG 质量评估。可以引入 RAGAS 等评估框架，对回答的 faithfulness、relevancy、context recall 做量化打分
>
> 6. **工具挂载**：目前工具虽然写好了但没有挂载到 chat 路由的 Agent 上，需要在 chat.py 里传 `tools=[...]` 让 Agent 真正能用工具调用

---

### Q11: 你的 JWT 认证和权限控制是怎么做的？

**回答**：

> 用 PyJWT 库签发和验证 JWT。登录成功后生成 token，payload 里只放 user_id 和过期时间（exp），用 HS256 算法签名。
>
> 认证流程：FastAPI 的 `get_current_user` 依赖从 Authorization header 取 token → 去掉 "Bearer " 前缀 → `jwt.decode()` 解出 user_id → 查数据库确认用户存在且 is_active=1 → 返回 user 对象。
>
> 权限控制用 `require_role` 函数：接收一个 UserRole 枚举，返回一个依赖函数，检查当前用户角色是否匹配。管理员（ADMIN）有所有权限，普通用户只能访问自己的资源。比如删除知识库需要 `require_role(UserRole.ADMIN)`，而创建知识库只需要 `get_current_user`（登录即可）。
>
> JWT 解码用 `asyncio.to_thread` 包装，避免阻塞事件循环。

### Q12: 你在开发过程中遇到的最难的问题是什么？

**回答**：

> 最难的是"暂无回答"这个 bug 的排查。现象是：不管问什么，前端都显示"暂无回答"，但后端日志里没有任何报错。
>
> 排查过程：
> 1. 先看前端 SSE 事件流，发现只有 `sources` 事件，没有 `content` 事件——说明后端生成器没 yield 内容
> 2. 看 chat.py 的异常处理，发现 `except Exception as e: yield error` 被触发了，但错误信息是 "Checkpointer requires configurable keys"
> 3. 追到 agent.py，发现 `config_kwargs={"configurable": {"thread_id": "..."}}` 被用 `**` 展开后直接传给 `astream`——但 langgraph 的 astream 第二个参数是 `config`，不是 `configurable`，所以 checkpointer 找不到 thread_id
> 4. 修好这个后又发现即使不报错，生成器还是不 yield——因为 `stream_mode="messages"` 产出的是 `(message, metadata)` 元组，原代码用 `event[1]` 取消息，但 event[1] 是 metadata dict，`isinstance(AIMessageChunk)` 永远 False
>
> 两个 bug 叠加：第一个 bug 导致异常，异常被 catch 后走 error 流；即使修好第一个，第二个 bug 又让生成器静默不产出。最终两个都修了才真正跑通。
>
> 教训是：异步生成器的调试比同步代码难得多，因为异常可能被 catch 后吞掉，而且 stream 的数据结构需要仔细看文档确认。

## 五、技术选型理由

| 技术 | 选型理由 |
|------|---------|
| FastAPI | 原生异步、自动 OpenAPI 文档、依赖注入系统 |
| LangChain | RAG 链式编排标准库，丰富的 Loader/Retriever/Splitter 生态 |
| LangGraph | Agent 状态机 + checkpointer 记忆，比 LangChain AgentExecutor 更灵活 |
| ChromaDB | 轻量级向量数据库，无需额外部署服务，collection 机制天然支持多知识库隔离 |
| MySQL + async SQLAlchemy | 关系型数据用成熟方案，async session 不阻塞事件循环 |
| 阿里云通义千问 | 国内访问稳定，dashscope SDK 封装完善，支持 OpenAI 兼容模式 |
| BM25Retriever | 经典关键词检索算法，与向量检索互补 |
| dashscope TextReRank | 专用 Rerank 模型，比向量余弦相似度更精准 |
